# Supabase Auth with Easyhook

Connect a Supabase project to deliver access codes and MFA by SMS,
WhatsApp or WhatsApp with SMS backup. The configuration is made in **Portal →
Integrations → Supabase Auth**; your application continues using the regular
Supabase SDK.

## Why Easyhook does not appear as a provider

Easyhook does not appear in Supabase's list of native phone providers. That list
contains adapters bundled directly with Supabase. Easyhook uses the Supabase
**Send SMS Hook**, which supports regional providers, WhatsApp, and fallback strategies.

Do not select another provider as a substitute, and do not put an Easyhook API
key in Supabase or your frontend. When you connect the project from Easyhook,
the portal uses Supabase OAuth to enable Phone Auth, create a dedicated signing
secret, and install the hook for that project.

## Connect a project

1. In Easyhook, open **Integrations → Supabase Auth** and connect your Supabase account.
2. Select the project and delivery mode.
3. Choose the SMS number or the appropriate WhatsApp number and template, along with its language (`es`, `en`, or `pt-BR`).
4. Confirm the connection. If a Send SMS Hook already exists, Easyhook shows
   that it will be replaced and preserves its configuration so it can be restored on disconnect.
5. Press **Verify**. Easyhook confirms that Phone Auth and the exact hook for
   this integration are still active.

You can also see the installed hook in **Supabase → Authentication → Hooks**.
You don't need to set up a native SMS provider.

## Delivery modes

- **SMS:** uses an active Easyhook number with outbound SMS.
- **WhatsApp:** uses an approved `AUTHENTICATION` template for a connected WhatsApp number.
- **WhatsApp with SMS fallback:** tries WhatsApp first and sends SMS only if
  that delivery fails; it does not intentionally send two codes.

The selection is configured per project. Supabase's Send SMS Hook does not
include a channel selected by the frontend, so `options.channel` cannot switch
between SMS and WhatsApp for each request when this hook is used.

## WhatsApp requirements

Easyhook shows this option when it finds at least one approved and synchronized
`AUTHENTICATION` template in the organization. Meta may require business
verification before allowing this template category; template approval is the
signal Easyhook can verify.

If it does not yet appear:

1. Connect the WhatsApp number to Easyhook.
2. Create the authentication template from **Templates**.
3. Wait for Meta's approval and synchronize the templates.
4. Go back to the integration of Supabase.

## Application code

Request the code from Supabase. If CAPTCHA is enabled in the project, also send
the token generated by your frontend:

```ts
const { error } = await supabase.auth.signInWithOtp({
  phone: "+15550100003",
  options: {
    captchaToken,
    shouldCreateUser: false
  }
})
```

Always use E.164 (`+` followed by the country code and number) and preserve the
exact same value when verifying. Remove `shouldCreateUser: false` only if you
want an unknown phone number to create a new account.

Check the code with Supabase:

```ts
const { data, error } = await supabase.auth.verifyOtp({
  phone: "+15550100003",
  token: code,
  type: "sms"
})
```

Supabase uses `sms` as the verification type for every phone OTP. That value
does not change when the code arrives through WhatsApp. The same delivery mode
applies to phone-based MFA challenges.

A successful OTP request confirms that Supabase accepted delivery through the
hook. Authentication is complete only when `verifyOtp` returns a session.

## Test from terminal

Use the project URL and publishable key. Never use `service_role` or a secret key
in a client-side test:

```bash
IFS= read -rp "Supabase URL: " SB_URL
IFS= read -rsp "Supabase publishable key: " SB_KEY; printf '\n'
IFS= read -rp "E.164 phone (+52...): " PHONE

curl -sS -X POST "${SB_URL%/}/auth/v1/otp" \
  -H "apikey: $SB_KEY" \
  -H "Content-Type: application/json" \
  --data "$(jq -nc --arg phone "$PHONE" '{phone:$phone}')" \
  -w '\nHTTP %{http_code}\n'
```

Write only the most recent code and check with the same phone.
The output is reduced to not print the session tokens:

```bash
IFS= read -rp "Most recent code: " OTP

VERIFY_RESPONSE=$(curl -sS -X POST "${SB_URL%/}/auth/v1/verify" \
  -H "apikey: $SB_KEY" \
  -H "Content-Type: application/json" \
  --data "$(jq -nc --arg phone "$PHONE" --arg token "$OTP" \
    '{type:"sms",phone:$phone,token:$token}')")

printf '%s' "$VERIFY_RESPONSE" | jq '{
  authenticated: (.access_token != null),
  user_id: .user.id,
  phone: .user.phone,
  error_code,
  msg
}'

unset SB_URL SB_KEY PHONE OTP VERIFY_RESPONSE
```

Supabase may default to a 60-second OTP validity period, so the application
should immediately display the code input. For a controlled manual test, you can
temporarily extend validity—for example, to 300 seconds—in the project's phone settings.

## Troubleshooting

| Error | What does it mean? |
| --- | --- |
| `captcha_failed` | Supabase stopped the request before calling Easyhook. Generate a fresh `captchaToken`; disable CAPTCHA only during a controlled test. |
| `phone_provider_disabled` | Phone Auth or the hook is inactive. Use **Verify** in Easyhook; do not choose a different native provider. |
| `unexpected_failure` / `Invalid payload sent to hook` | Supabase called the hook, but it returned an error. Record the `error_id` and review integration and delivery logs. |
| `otp_expired` | The code may have been delivered correctly, but it has already expired, was replaced or checked with another phone. It requests a new one and uses only the latest one. |
| HTTP `429` | You reached the resend interval or a Supabase limit. Wait before requesting another code. |

Do not repeatedly request codes for diagnosis: each accepted request can create
a delivery and charge. Delivery acceptance and successful code validation are
two different stages.

## Privacy and charges

- The OTP does not appear in Inbox, client webhooks or integration records.
- Each accepted request charges one Easyhook API operation.
- If SMS is used, the SMS is also charged at the current rate.
- If WhatsApp works, Easyhook doesn't charge an SMS.
- In fallback mode, SMS is charged only when the fallback is attempted.
- WhatsApp authentication template charges are applied to the account
  from WhatsApp connected according to the current rates of Meta.

Easyhook verifies that the number, WhatsApp connection, and template belong to
the same organization. It never uses another organization's resources as fallback.
